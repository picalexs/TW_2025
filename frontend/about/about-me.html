1. Introduction

1.1 Purpose

This document describes the software requirements for the web application Pet Adoption Center, version 1.0. This document covers all primary functionalities of the system, including the user registration/authentication process, publishing and viewing adoption listings, pet management, the compatibility test, and the sharing and review features.

1.2 Document Conventions

In this document, functional requirements are marked with the prefix "FR-" (e.g., FR-1), and non-functional requirements are marked with "NFR-".

All critical requirements are highlighted in bold, and technical terms are written in italics.

This document is structured according to the IEEE standard for SRS.

1.3 Intended Audience and Reading Suggestions

This document is intended for the development team (composed of two students) and the supervising professor for the seminar, for the purpose of evaluating and validating the requirements of the Pet Adoption Center application. The document provides a detailed overview of the planned functionalities and the technical and non-technical requirements that will guide the project's implementation.

The following reading order is suggested:

  • Section 1 for a general overview of the application's purpose and context.
  • Section 2 for an understanding of the product's overall structure.
  • Section 3 and onwards for a detailed breakdown of functional and non-functional requirements.

1.4 Product Scope

Pet Adoption Center is a web application designed to facilitate the pet adoption process. The application allows authenticated users to publish listings for pets available for adoption, search for animals based on location, breed, or other relevant factors, and receive personalized suggestions based on a compatibility test. The application's goal is to digitize and streamline the process of adopting and caring for animals, promoting social responsibility and animal welfare.

1.6 Core Technology Rationale

    Design Rationale: Colors, Fonts & UI Choices

    • Colors: The palette uses shades of blue, gray, and white to create a professional, calm, and friendly atmosphere. The light backgrounds (#f7f9fa, #f0f4f8) reduce visual fatigue, while blue accents (#3498db, #2a3a4a) convey trust and clarity—qualities suitable for social and educational applications.
    • Fonts: Segoe UI (with Arial, sans-serif as fallback) was chosen for its excellent readability on all devices, modern look, and wide compatibility. This font is standard on Windows and widely used in professional web applications.
    • Contrast & Accessibility: Strong contrast between text and background ensures readability, including for users with visual impairments. Font sizes are generous, and interactive elements (links, buttons) have visible hover/focus states.
    • Structure & Spacing: Margins, padding, and border-radius are used to clearly separate sections, provide breathing room, and create a pleasant, uncluttered visual experience.
    • Responsiveness: The layout and styles are optimized for both desktop and mobile, with media queries for font and spacing, ensuring a consistent experience on any screen.
    • Visual Consistency: All components (ToC, meta-info, tables, code) use the same modern style for a unified and professional visual identity.

    Design Rationale: Use of JavaScript

    • Universality: JavaScript is the only programming language natively supported by all modern web browsers, making it the standard for client-side interactivity and dynamic content.
    • Interactivity: JavaScript enables dynamic features such as language switching, navigation highlighting, form validation, and asynchronous API calls, all of which are essential for a modern, user-friendly web application.
    • Framework-Free Approach: The project requirements explicitly prohibit the use of frameworks (like React, Angular, Vue), so JavaScript is used in its native form ("vanilla JS") to implement all dynamic behaviors, ensuring transparency and full control over the codebase.
    • Maintainability & Modularity: JavaScript allows for modular code organization (separate files for language management, routing, widgets, etc.), making the application easier to maintain and extend.
    • Performance: Native JavaScript is lightweight and fast, with no dependency overhead, which helps the application load quickly and run efficiently on all devices.
    • Accessibility & Standards: JavaScript is used to enhance, not replace, semantic HTML. All dynamic features are implemented with accessibility in mind, ensuring keyboard navigation and ARIA support where needed.

2. Overall Description

2.1 Product Perspective

The Pet Adoption Center application is a new software product, developed as an educational project for the Web Technologies course. It is not part of an existing product family and does not replace any functioning systems. It is a self-contained web application that manages the pet adoption process.

The system consists of two main components:

  • Web Frontend – the graphical user interface.
  • Backend API – which manages application logic and communication with the database.

The application will communicate with:

  • External authentication services (e.g., Google OAuth 2.0).
  • RSS sharing systems.
  • An Oracle database that stores information about users, animals, and their history.

2.2 Product Functions

  • User authentication and registration (including Google Auth, email verification).
  • User profile management (view, edit, upload photo).
  • Add, edit, and view animals (with images, details, tags).
  • Favorites system (users can save favorite animals).
  • Matching between users and animals (based on preference tags).
  • Matching test (user completes a test, preferences are saved).
  • Animal recommendations (based on matching score).
  • Reviews (users can leave reviews for owners).
  • Notification system (notifications for relevant actions).
  • User administration (admin can view and delete users, with protection for admins + export tables).
  • RSS Feed (export and view RSS feed with animals).
  • Multi-language interface (EN/RO, with a complete translation system).
  • Portable pet widget (can be integrated into external websites).
  • Presentation and demo pages (about, home, test, etc.).

2.3 User Classes and Characteristics

User Class Characteristics
Authenticated Users (families / individuals) Access main functions: adoptions, adding listings, viewing animals, matching test. Technical level: low/medium.
Administrator Has access to moderation functions (delete accounts, export all tables). Technical level: medium/high.
Unauthenticated Visitors Can only view public listings and access the RSS feed. Cannot interact actively.

2.4 Operating Environment

Backend
Node.js (custom Express-like router), running on a server (e.g., localhost:8080).
Frontend
HTML, CSS, JavaScript (without modern JS frameworks).
Database
Oracle Database (uses the oracledb package for Node.js).
File System
Separate structure for backend and frontend.
Email
Nodemailer for sending emails (e.g., account confirmation).
Development Environment
Local (Windows), but portable to any system with Node.js and Oracle DB.

2.5 Design and Implementation Constraints

  • No Web Frameworks: The use of modern frameworks on both the client-side (e.g., React, Angular, Vue) and server-side (e.g., Express, NestJS) is not permitted. The code must be written using native technologies.
  • Web Services-Based Architecture: All application functionalities will be exposed through API-type services. Their invocation by the client interface will be done asynchronously, using technologies from the Ajax suite (XMLHttpRequest or fetch() in JavaScript).
  • Valid HTML5/CSS3 Interface: The HTML code will be written according to W3C standards for HTML5. The CSS will follow best practices.
  • Open License: Only technologies, languages, and platforms that adopt open licenses will be used (e.g., Node.js, Oracle Express Edition, JavaScript).
  • Flexible Database: For data storage and management, the system will use an Oracle relational database, queried via SQL.
  • Templates and Configurability: The application will use templates for presentation and include simple configuration and administration methods (e.g., .env files for configuration variables).
  • Full Requirement Fulfillment: The application must meet all functional and non-functional requirements specified in the project statement.

2.6 User Documentation

The following support materials will be delivered:

  • A demonstration video.

2.7 Assumptions and Dependencies

  • Depends on Node.js and npm packages: oracledb, nodemailer, dotenv, etc.
  • Depends on an Oracle Database instance (requires user, password, and connect string configured in .env).
  • An assumption is that no frameworks (React, Vue, Angular, etc.) will be used.
  • The translation system assumes the existence of JSON files for each language and page.
  • Animal and user images are stored locally on the server's file system.
  • Emails are sent only if the environment variables are correctly configured.
  • Access to admin functions is restricted by roles in the database.
  • There are no dependencies on cloud or external services, except for email and Google Auth.

3. External Interface Requirements

3.1 User Interfaces

  • Technologies Used: HTML5, CSS3, Vanilla JavaScript. CSS is modularized by page/feature. The interface language is managed through JSON files.
  • Typical Page Structure:
    • Global Header: with logo, navigation, authentication buttons, and language switcher.
    • Main Content: sections for listing animals, pet details, matching, favorites, profile, admin, etc.
    • Global Footer: with contact information, useful links, copyright.
  • Common Elements: Reusable navbar and footer. Cards for animals, users, reviews. Consistently styled buttons. Internationalized feedback and error messages.
  • Responsiveness: CSS Grid and Flexbox for an adaptive layout. Media queries for optimization on mobile/tablet.
  • Accessibility: Semantic use of HTML tags (header, nav, main, footer). Good contrast, legible fonts, visible focus on interactive elements. Keyboard navigation and form labels.

3.2 Hardware Interfaces

The application is a purely software solution with no dedicated hardware components. It operates on standard client and server hardware.

  • Client: A modern web browser on any desktop or mobile device.
  • Server: A standard server or cloud VM capable of running Node.js and an Oracle DB client.

3.3 Software Interfaces

The application interacts with the following software components:

  • Database: Oracle Database, accessed via the oracledb Node.js package.
  • Environment Variables: Used for DB credentials and other secrets, loaded via a .env file.
  • Node.js APIs: Standard Node.js modules are used to build the backend.
  • Frontend/Backend API: A RESTful API is used for communication. Endpoints for users, pets, favorites, etc., are consumed by the frontend JavaScript.
  • Portable Widget: Can be embedded on external sites via a JavaScript file.

3.4 Communications Interfaces

  • HTTP/HTTPS: All communication between the client and server is via HTTP(S). JSON is the primary data format for API requests and responses.
  • CORS: The server is configured to allow cross-origin requests to support the portable widget and frontend.
  • Web Embedding: The portable widget can be embedded on third-party sites, communicating with the backend via HTTP(S).

4. System Features

4.1 User Authentication and Authorization

Description and Priority: Provides secure user registration, login, and role-based access. Priority: High.

Stimulus/Response Sequences:

  • User submits registration form → System validates and creates the user or returns an error (e.g., username/email exists).
  • User submits login form → System authenticates and returns a session/token or an error.

Functional Requirements:

  1. FR-1.1: The system must validate unique usernames and emails.
  2. FR-1.2: The system must hash and securely store passwords.
  3. FR-1.3: The system must provide JWT or session-based authentication.
  4. FR-1.4: The system must restrict access to protected routes based on user roles (user, admin).
  5. FR-1.5: The system must return clear error messages for invalid credentials or duplicate accounts.

4.2 Pet Management

Description and Priority: Allows users and admins to add, edit, view, and delete pet profiles. Priority: High.

Stimulus/Response Sequences:

  • Admin/user submits a new pet form → System validates and saves the pet data.
  • User views the pet list → System returns paginated and filterable pet data.

Functional Requirements:

  1. FR-2.1: The system must allow authenticated users to perform CRUD operations for pet profiles.
  2. FR-2.2: The system must validate all required fields (e.g., name, species, age) and their data types.
  3. FR-2.3: The system must prevent the deletion of a pet if it is referenced in other records (e.g., adoption history).
  4. FR-2.4: The system must support image uploads and display for pet profiles.

4.3 Favorites and Matching

Description and Priority: Users can favorite pets and receive recommendations based on a tag-matching algorithm. Priority: High.

Stimulus/Response Sequences:

  • User clicks the "favorite" button on a pet → System adds/removes the pet from the user's favorites list.
  • User requests recommendations → System returns a list of pets sorted by their matching score.

Functional Requirements:

  1. FR-3.1: The system must allow users to add or remove pets from their personal favorites list.
  2. FR-3.2: The system must calculate and return a matching score based on overlapping tags between user preferences and pet characteristics.
  3. FR-3.3: The system must handle errors for invalid or missing data gracefully.

4.4 Admin Panel

Description and Priority: Admins can manage users, pets, and system data via a dedicated interface. Priority: Medium.

Stimulus/Response Sequences:

  • Admin logs in → System displays the admin dashboard with relevant statistics and management tools.
  • Admin deletes a user → System checks for dependencies and confirms the deletion.

Functional Requirements:

  1. FR-4.1: The system must provide a secure admin dashboard accessible only to users with the 'admin' role.
  2. FR-4.2: The system must allow admins to perform CRUD operations on all users and pets.
  3. FR-4.3: The system must allow admins to export data from main tables (e.g., Users, Pets) into a downloadable format (e.g., CSV).

5. Other Nonfunctional Requirements

5.1 Performance Requirements

  • The system must support at least 50 concurrent users without significant degradation in response time (target: <1s for standard queries, <3s for complex reports).
  • The backend shall establish and manage a connection pool to the Oracle database for efficient query execution.
  • The frontend must load and render the main user interface in under 2 seconds on a standard broadband connection.
  • Widget and API responses should be delivered within 1 second under normal load.

5.2 Safety Requirements

  • The application must prevent data loss by using transactions for critical database operations (e.g., user registration, pet adoption).
  • Only authorized users can perform destructive actions (e.g., deleting pets or users).
  • The system must log all errors and critical events for auditing and recovery purposes.
  • File uploads must be validated to prevent the storage of malicious content.

5.3 Security Requirements

  • All user passwords must be securely hashed and never stored in plain text.
  • User authentication is required for all protected routes; JWT or session tokens shall be used.
  • Sensitive operations (e.g., admin actions, data deletion) require elevated privileges (admin role).
  • The system must validate all user input to prevent common web vulnerabilities like SQL Injection, XSS, and CSRF.
  • Database credentials and other secrets must be stored in environment variables, not in the source code.
  • The system should comply with data privacy best practices (e.g., allowing users to delete their own account and associated data).

5.4 Software Quality Attributes

Availability
The system should be available 99% of the time, excluding scheduled maintenance.
Reliability
All critical operations must be robust against database or network errors, providing clear error messages and fallback behavior.
Maintainability
The codebase is modular, with a clear separation of concerns between frontend, backend, and database logic.
Portability
The frontend is browser-agnostic and responsive; the backend can run on any Node.js-compatible environment.
Usability
The UI is designed to be intuitive, with clear navigation, user feedback, and accessibility features (ARIA, keyboard navigation).
Testability
The system's modular design supports unit and integration testing for both backend and frontend logic.
Interoperability
The portable widget can be embedded on external sites and communicates via a standard HTTP API.

5.5 Business Rules

  • Only authenticated users can add pets to favorites, adopt pets, or access their profile.
  • Only admins can manage all users, all pets, and system-wide data.
  • Each user must have a unique email and username.
  • Pets cannot be deleted if they are referenced in other records (e.g., adoption history), enforced by referential integrity.
  • The portable widget may only display public pet data; sensitive user data is never exposed externally.
  • All user actions are subject to role-based access control.

6. Other Requirements

Database Requirements

  • The application uses Oracle Database as the primary DBMS, accessed via the Node.js oracledb driver.
  • The database schema enforces referential integrity, unique constraints, and data validation through triggers and constraints.

Internationalization Requirements

  • The frontend supports multiple languages (at least English and Romanian) using JSON files for all user-facing text.
  • The language can be switched dynamically by the user, and the system remembers the preference.

Legal Requirements

  • User data is handled in compliance with privacy best practices.
  • Open-source libraries are used in accordance with their respective licenses.

Reuse Objectives

  • The portable pet widget is designed for easy integration on external websites.
  • Backend logic is modular (controllers, models, DTOs, utilities) to facilitate future feature expansion and code reuse.

Accessibility Requirements

  • The frontend uses semantic HTML and ARIA attributes where appropriate to ensure accessibility.
  • Color contrast and font sizes are chosen for readability.
  • All interactive components are keyboard-accessible.

Appendix B: Analysis Models

Entity-Relationship Diagram (ERD)
The project uses an Oracle database with entities such as User, Pet, Favorite, and Review, and relationships like user-pet favorites, user-pet reviews, and pet ownership.
Data Flow
  1. The user interacts with the frontend (HTML/JS/CSS).
  2. The frontend sends asynchronous requests to the backend API endpoints.
  3. The backend processes requests, interacts with the Oracle DB, and returns JSON responses.
  4. For the widget, an external site loads the widget script, which then fetches and displays pet data from the backend API.
